## 1. Executive summary

**CinemapProvider: UNSUPPORTED.** Клиентская цепочка разрешения видео восстановлена до границы серверного API. Это существенно больше, чем обнаружение временного HLS: найдено происхождение тела запроса, порядок преобразований, мутация элементов PlayerJS и повторное разрешение ссылки. Однако подтверждённого публичного контракта для поиска контента, получения актуального embed/дескриптора и использования HLS в стороннем AVPlayer пока нет. Наличие доступного браузеру endpoint само по себе такой контракт не устанавливает.

**Главный результат:** в исследованном Cinemar поле `currentItem.data` не вычисляется из `vid`, `cuid`, `ssid` или HLS. Оно уже содержится в данных, переданных через `Cinemar(options)`: после декодирования `options.file` становится свойством листового JSON-объекта. Обход дерева сохраняет ссылку на этот объект; выбор назначает его `currentItem`; HTTP helper отправляет `JSON.stringify(currentItem.data)`. Отдельного генератора этого значения в данной цепочке нет. После ответа сервер может заменить любое поле через `Object.assign`, включая `data`, если оно присутствует в ответе. [1: строки 26526–26559, 26660–26684, 27013–27015]

Обозначения доказательности:

- **CONFIRMED — CODE:** непосредственно установлено по локальному JS или исходникам приложения.
- **CONFIRMED — PROVIDED NETWORK:** присутствует в предоставленном описании сетевого наблюдения; самостоятельно не воспроизведено, полного HAR нет.
- **CONFIRMED — LOCAL TEST:** проверено на извлечённой функции с синтетическими данными, без сети.
- **LIKELY:** объяснение согласуется с данными, но остаётся гипотезой.

## 3. Cinemar initialization

`Cinemar(options)` получает готовую конфигурацию от вызывающего HTML. Обёртка рассчитывает предпочтительное качество по размерам окна, создаёт API helper, playlist manager, resume/download/HLS/VAST handlers. Затем задаёт параметры PlayerJS и начинает preload. [1: 26446–26468, 27000–27023]

Call graph с входами и результатами:

```text
HTML: Cinemar(options)
  ├─ настройки quality / poster / hlsconfig / VAST
  └─ playlist.preload(options.file, hidePlaylist, playback.id, callback)
       ├─ load(options.file) → дерево → self.playlist
       │    ├─ object → вернуть тот же объект
       │    └─ #2 string → loadFromString → slice → readString → JSON.parse
       ├─ buildFlattenPlaylist(self.playlist) → ссылки на листья → self.flatlist
       ├─ find сохранённого id либо flatlist[0] → currentItem
       └─ loadMedia(callback)
            └─ api.post("playlist/load", currentItem.data, result, cleanup)
                 └─ XHR → JSON.parse → unwrap response.data, если есть
                      └─ Object.assign(currentItem, result)
                           └─ callback(self.playlist)
                                └─ options.file = дерево
                                     └─ new Playerjs(options)
                                          ├─ IndexPlaylist / IndexPlaylistProcessor
                                          └─ выбранный item.file → media engine
                                               └─ HLS manifest → segments
```

Первый `playlist/load` происходит **до** `new Playerjs(options)`. Следовательно, библиотечная индексация PlayerJS не нужна для генерации первого `data` и не может быть его первоначальным источником. [1: 26536–26559, 27013–27015]

## 4. options.file

Здесь необходимо различать три разных значения с одинаковым именем:

| Значение | До/после какого действия | Содержание |
|---|---|---|
| `options.file` при входе | До `preload` | Упакованная строка `#2…` либо готовый объект |
| `options.file` перед PlayerJS | После успешного первого `loadMedia` | Массив дерева playlist |
| `currentItem.file` | После `Object.assign` ответа API | Медиаисточник; в предоставленном ответе — HLS URL |

`#238IyJ9XQ3e...` — сокращённый образец. `#2` является маркером формата, следующие два символа `38` задают код разделителя. Многоточие не позволяет восстановить полный JSON или проверить побайтовое совпадение известного payload с полем `data`. Сам `vid` не содержит достаточных данных для восстановления сокращённого `file`. [1: 26660–26684; 2]

## 5. Playlist decoding

**CONFIRMED — CODE:** точная последовательность:

1. `load(e)` возвращает объект непосредственно, если `typeof e == "object"`. Для строки проверяет префикс `#2`, убирает его через `e.substr(2)` и вызывает `loadFromString`.
2. `loadFromString(e)` сохраняет первые два символа в `self.dm`, устанавливает `self._ml = 32` и передаёт остаток в `slice`.
3. `slice` делит строку по `String.fromCharCode(self.dm)`. Для `38` это `&`. Для каждого фрагмента берётся число `t` из последнего символа; если длина больше 32, возвращается `e.substr(2*t, e.length-3*t-1) + e.substr(0,t)`. Короткие фрагменты сохраняются. Результаты соединяются пустой строкой.
4. `readString` добавляет Base64 padding `=` до длины, кратной четырём.
5. Индексы действий `1,5,15,12` в `self.ex` означают **`atob → escape → decodeURIComponent → JSON.parse`**. `escape` здесь нельзя пропустить: это часть преобразования байтовой строки в Unicode.
6. Возвращённый JSON-объект становится `self.playlist`.

Источники: [1: 26538, 26660–26684, 26793].

Это обратимое клиентское преобразование **внешнего контейнера**. Оно не является доказательством расшифровки внутреннего `data`. `JSON.parse` создаёт свойство объекта из сериализованного JSON; он не создаёт новый серверный токен. В списке `self.ex` присутствует `btoa`, но выбранная последовательность его не вызывает.

Проверка извлечённого closure на искусственном дереве `season → episode → voice` с `data="SYNTHETIC_DESCRIPTOR"` прошла. Реальные дескрипторы не генерировались и не отправлялись.

## 6. Playlist structure

Читаемый wrapper ожидает дерево массивов. Узел с `folder` рекурсивно раскрывается, лист без `folder` добавляется в `flatlist`. UI показывает `title`, использует `id`, а наличие `data` отличает запускаемый вариант при построении переключателей. [1: 26526–26528, 26564–26640]

Следующая форма — **схема по потребителям кода, не декодированный реальный фильм**:

```text
[
  {
    id: исходный идентификатор группы,
    title: отображаемое имя,
    folder: [
      {
        id: исходный идентификатор листа,
        title: отображаемое имя варианта,
        data: непрозрачный дескриптор из входного JSON,
        file: исходное значение, если было; затем значение API,
        ...другие поля
      }
    ]
  }
]
```

После создания PlayerJS функция `IndexPlaylistProcessor(x,y,p,j)` мутирует элементы:

- существующий `id` копирует в `pjs_id`;
- создаёт внутренний `id` вида `"x" + parent + "-" + index + optionalOriginalId`;
- задаёт `pjs_parent`, `pjs_parent_i`, `pjs_i`;
- может заменить `title` значением `comment`;
- поддерживает alias `playlist → folder` и дополнительную обработку `file`.

Эти действия подтверждены в распакованной строке 26, `IndexPlaylistProcessor`, смещения около 360440–361500. Поэтому нельзя считать `currentItem.id` неизменным серверным идентификатором на всех этапах. `pjs_parent` — клиентская структура PlayerJS, а не доказанное поле серверного каталога. [1]

## 7. currentItem

`currentItem` объявлен локально внутри playlist closure, первоначально без значения. Все назначения в читаемой обёртке:

| Место | Назначение | Смысл |
|---|---|---|
| 26540–26543 | `flatlist.find(id)` либо `flatlist[0]` | Восстановить выбор или взять первый лист |
| 26603 | `currentItem = e` | Выбор листа в UI |
| 26609 | `findFirstMediaItem(e.folder)` | Выбор вложенной группы |
| 26655–26656 | `flatlist.find(pjs_id/id)` | `goto` по идентификатору |
| 26765 | совпавший `title` либо первый лист соседней группы | Next/Previous |

`buildFlattenPlaylist` выполняет `push(t)`, не `map` в новый объект и не копирование полей. `currentItem` и соответствующий лист дерева ссылаются на один объект. Поэтому `Object.assign(currentItem, response)` обновляет также дерево, которое получает PlayerJS. Это подтверждено синтетическим тестом сравнения объектов через строгое равенство. [1: 26526–26559]

`currentItem.title` изначально берётся из входного JSON; библиотека может нормализовать его через `comment`. `currentItem.file` после разрешения берётся из API response. `currentItem.data` изначально берётся из JSON, а не из этих двух полей.

## 8. Origin of currentItem.data

Полная цепочка присваиваний:

```text
HTML/embed формирует аргумент Cinemar({file: исходноеЗначение, ...})
  → параметр options функции Cinemar
  → options.file
  → playlist.preload(e = options.file, ...)
  → self.playlist = load(e)
  → loadFromString(e.substr(2))                         [для #2]
  → slice(остаток после dm)
  → readString(..., 1, 5, 15, 12)
  → atob → escape → decodeURIComponent → JSON.parse
  → JSON-дерево с уже сериализованными полями листов data
  → buildFlattenPlaylist: self.flatlist.push(t)         [тот же объект]
  → currentItem = найденный лист либо self.flatlist[0]
  → loadMedia()
  → api.post("playlist/load", currentItem.data, ...)
  → post(e, n, i, a): n = currentItem.data
  → o(e, "POST", n, i, a, retryCount): i = n
  → s.send(JSON.stringify(i))
  → HTTP body
```

**HERE THE VALUE FIRST APPEARS IN CLIENT CODE:** в аргументе `options.file` значение уже представлено внутри входного контейнера; как отдельное доступное свойство `.data` оно впервые материализуется в результате `JSON.parse`. Для объектного `options.file` свойство уже доступно при входе и декодер пропускается. [1: 26446, 26538, 26660–26678]

В читаемом wrapper отсутствует отдельное присваивание `currentItem.data = …`, генерация из `vid` или преобразование этого поля перед POST. Поиск прямых `.data =` и `['data'] =` в статически распакованном PlayerJS также не выявил генератора дескриптора: обнаруженное `zv["data"]=y` относится к сообщениям событий `postMessage`, а не к playlist item. Общие присваивания и вложенные динамические части библиотеки не позволяют утверждать отсутствие любого возможного изменения при любой конфигурации; происхождение первого POST от этого не зависит, поскольку он предшествует созданию PlayerJS.

После ответа `Object.assign(currentItem,n)` не фильтрует поля. Если сервер вернёт `data`, оно будет заменено. В предоставленном ответе `data` отсутствует, поэтому такой ответ сохраняет старый дескриптор. Выбор другого листа меняет объект `currentItem`; его `data` может отличаться, но уникальность значений у разных листов не проверяется кодом. [1: 26556; 2]

**SERVER-GENERATED OPAQUE VALUE — LIKELY в части генерации; CONFIRMED в части непрозрачности для wrapper.** HTML поставляет значение извне; исходная серверная генерация не наблюдается. Подпись, шифрование, ключ, срок жизни, привязка к IP/сессии и алгоритм проверки — **UNKNOWN**. Непрозрачная Base64-похожая строка не доказывает ни конкретную криптографию, ни возможность её генерации клиентом.

Из-за сокращённого `file` нельзя подтвердить, что предоставленная длинная строка побайтово равна `data` именно этого embed. Доказан путь значения в данной версии кода, а не отсутствующий полный сетевой снимок.

## 9. playlist/load request

| Параметр | Подтверждённое поведение |
|---|---|
| Метод | POST |
| URL в коде | `/api/playlist/load` |
| Наблюдавшийся полный URL | `https://cinemar.cc/api/playlist/load` — PROVIDED NETWORK |
| Content-Type | `application/json`, если payload не null/undefined |
| Body | `JSON.stringify(currentItem.data)` |
| Для строкового data | JSON string literal с внешними кавычками; не JSON-объект `{data: …}` и не form body |
| Timeout | 3000 мс на XHR |
| Network/timeout retry | Один дополнительный запрос через 500 мс; максимум две попытки helper |
| HTTP 4xx/5xx | Ошибка callback, без этого network retry |
| Невалидный JSON | Ошибка callback, без retry |
| `success:false` | Ошибка с `response.error` |
| Успешный JSON | Если есть верхнеуровневое `data`, передаётся `response.data`; иначе весь response |
| Callback | Ошибка → Notice/collect; успех → `Object.assign` и callback в timer 0 |
| Cleanup | Убирает CSS `preload` после завершения helper |

Источник: [1: 26466–26514, 26551–26562]. При двух последовательных timeout ориентировочное ожидание helper — 6,5 секунды плюс задержки планировщика. Это не общий лимит всех попыток медиадвижка.

Обёртка не добавляет явные Authorization/Referer/cookie headers. Это **не доказывает отсутствие браузерных cookies**: обычный XHR может передавать их в допустимом контексте браузера. Не установлено, что сервер принимает тот же body вне embed. Нельзя приравнивать CORS-настройку к серверной авторизации.

## 10. playlist/load response

Предоставленный ответ содержит `file`, `duration=6217`, `thumbnails`, `download`, `subtitle=""`. Wrapper не описывает строгий response DTO: он объединяет полученный объект с выбранным листом. [1: 26556; 2]

| Поле | Назначение и подтверждение |
|---|---|
| `file` | Медиаисточник. В примере готовый `.m3u8`; PlayerJS получает его через playlist и передаёт URL медиадвижку |
| `duration` | Длительность/метаданные; PlayerJS переносит её из элемента в настройки. Не URL воспроизведения |
| `thumbnails` | Отдельный ресурс предпросмотра таймлайна; `PluginThumbs` делает XHR и разбирает разметку VTT |
| `download` | Непрозрачный дескриптор отдельного download flow; обёртка POST-ит его в `/api/player/download` и отображает полученный HTML |
| `subtitle` | Передаётся `o.actions.Subtitle(opid['subtitle'])` при выборе элемента; пустая строка в примере не подтверждает рабочие внешние субтитры |

Источники: [1: 26845–26880; распакованная строка 26, `UpdateVars` около 200568–201700, `PluginThumbs` около 230075–231000]; назначение thumbnails подтверждает также [документация PlayerJS](https://playerjs.com/docs/en=thumbnails).

`download` не используется вызовом `loadMedia` как URL основного playback. `thumbnails` относится к превью, но отсутствие рекламных/прочих данных внутри недоступного реального ресурса не проверено. Отдельные субтитры PlayerJS нельзя автоматически считать подключёнными в AVPlayer: потребуется поддерживаемый формат/интеграция, либо subtitle rendition в HLS.

## 11. HLS lifecycle

**CONFIRMED — CODE:** источник возвращает сервер; wrapper не строит CDN URL и не вычисляет его timestamp. В PlayerJS `CreateHLS` создаёт `Hls`, вызывает `hls.loadSource(url)` и `hls.attachMedia(pjstg)`. Присутствует и работа с native media `src`. Наблюдаемая веб-цепочка заканчивается браузерным движком; **AVPlayer в исследованном JS отсутствует**, он был бы новым потребителем в iOS-интеграции. [1: строка 26, около 392680–395000, 400000]

**LIKELY:** суффикс `:2026091408` похож на часовой маркер `YYYYMMDDHH`. Но JS не разбирает его как дату и не рассчитывает expiration. Повторный `playlist/load` показывает механизм повторного разрешения, а не доказывает точный TTL. Неизвестны часовой пояс, начало/конец окна, grace period и зависимость от других параметров. `expiresAt` нельзя надёжно заполнить из одного такого примера. [1; 2]

URL может перестать работать из-за срока действия, отзыва доступа, удаления ресурса, отказа CDN, сети или серверных ограничений. Конкретная причина требует HTTP status и серверного ответа. Само наличие `Referer` в наблюдении не доказывает, что сервер его проверяет.

При успешном reload сервер снова возвращает playback-объект. Поле `file` заменится возвращённым значением, которое **может оказаться тем же URL**. Гарантии новой ссылки или продления срока в клиентском коде нет. Истечение самого `data` отдельной процедурой обновления не обработано.

## 12. CDN routing

**CONFIRMED — PROVIDED NETWORK:** наблюдались `host.cinemap.cc`, `pegasus.host.cinemap.cc`, `oxygen.host.cinemap.cc`, а также redirect `pegasus → oxygen` и запросы `.ts` сегментов. Полный redirect status/Location/HAR не предоставлен. [2]

**LIKELY:** промежуточный узел выполняет маршрутизацию к доступной CDN-точке. Нагрузка, география, failover и распределение хранения — возможные причины, но ни одна не установлена. Называть pegasus обязательным центральным router нельзя: известен один описанный маршрут, а серверная топология недоступна.

В исследованном wrapper нет выбора между перечисленными hostname: используется серверный `file`. Нельзя фиксировать один CDN, заменять hostname в URL или переносить на другой хост подписанные параметры. Для будущего провайдера исходным является полный URL из разрешённого ответа; media engine обрабатывает допустимые HTTP redirects. Политика переноса чувствительных headers между origin потребует отдельного контракта.

## 13. Reload mechanism

`playlist.reload(e)` [1: 26773–26787]:

1. Запоминает `floor(player.api("time"))` и состояние `playing`.
2. Ставит воспроизведение на паузу, если оно шло.
3. При truthy аргументе `e` использует его как позицию; нулевой аргумент текущую позицию не заменяет.
4. Вызывает обычный `loadMedia`, который снова POST-ит **текущее** `currentItem.data`.
5. После ответа находит обновлённый item, восстанавливает позицию больше одной секунды и запускает playback.
6. Если до reload была пауза, временно mute/play и через 100 мс pause/unmute восстанавливают паузу.

Внутренний маркер `[skipads]` в `find` используется самим wrapper при восстановлении того же элемента. Это описание существующего resume flow, не инструкция по удалению рекламы.

Два разных уровня повторов нельзя смешивать:

| Уровень | Условие | Поведение |
|---|---|---|
| API helper | XHR network error или timeout | Один retry через 500 мс |
| HLS wrapper | `networkErrorHls`, кроме отдельной ветки `manifestLoadError`, если не fatal/loading | Считает ошибки; после порога 3 увеличивает счётчик reload; первые два цикла планируют reload через 1000 мс |
| HLS wrapper после лимита | `retriesCount > 2` | Fatal и предложение ручного повтора |
| `manifestLoadError` | Отдельная ветка события | Сразу fatal; автоматического reload в этой ветке нет |

Успешный fragment сбрасывает `failsCount` и флаги, но не `retriesCount`. Смена item при событии `new` сбрасывает и счётчик повторов. Пока `loading=true`, новые HLS errors игнорируются этим обработчиком. Библиотечные внутренние retries Hls.js являются дополнительным уровнем, поэтому «всего ровно два сетевых запроса» неверно. [1: 26881–26942, 26977–26998]

**Следствие:** утверждение «любой истёкший HLS автоматически обновится» не подтверждается; manifest failure уже имеет исключение, а отказ самого `/playlist/load` отображается как ошибка. Embed/config заново не запрашиваются.

## 14. Ads/VAST

Параметры `preroll`/`midroll` передаются в `new Playerjs(options)` вместе с остальной конфигурацией. VAST — отдельная подсистема библиотеки: распакованная строка 26 содержит загрузку рекламного XML (`LoadXmlCredentials`, около 106537), разбор VAST и дальнейший выбор рекламного media. Это отдельный путь от `playlist/load` основного контента. [1]

Midroll-планировщик PlayerJS читает `time`, переводит процент в `parseInt(percent) * duration / 100` и сравнивает с текущим временем; есть дополнительные ограничения показа и обработки seek. Поэтому `time:"40%"` означает точку около 40% длительности, когда выполнены остальные условия, а не 40% URL/TTL. Код находится около смещения 349538; это согласуется с [официальным описанием параметров рекламы](https://playerjs.com/docs/en=managevast) и [midroll](https://playerjs.com/docs/en=midroll).

Wrapper обрабатывает `vast_Impression` и отправляет `/api/player/vast` с JSON-строкой, составленной из `options.host`, типа показа и id объявления. `options.host` также подставляется в `{host}` через `vast_replace`. При инициализации установлены лимиты preroll=4 и midroll=1; по timer они обновляются до 5 и 2. Выражение `60 * 5 * 60 * 1000` означает **5 часов**, проверка выполняется каждые 10 секунд. [1: 26944–26966, 26997, 27008–27010]

В download flow отдельно используется `options.vast && options.dp_vast`, выбирается preroll и может вызываться `startvastandwait` перед обработкой download. Само поле `dp` wrapper напрямую не читает; его полный смысл по предоставленной конфигурации не установлен. [1: 26845–26880]

**Вывод:** CONFIRMED — предусмотрена отдельная клиентская VAST-реклама. **UNKNOWN — отсутствует ли любая встроенная реклама в самом фильме/HLS.** Для такого вывода нужны manifest/медиа и наблюдение конкретного воспроизведения. Раздельные рекламные параметры не доказывают отсутствие server-side insertion или рекламных кадров в исходнике. Условия допустимой сторонней интеграции рекламы также не установлены.

## 16. Series

Обёртка поддерживает произвольное дерево `folder`. `self.is_serial = !!self.playlist[0].folder` — эвристика интерфейса, а не строгий тип контента: папки могут представлять и варианты фильма. В Cinemar wrapper не обнаружено отдельного запроса каталога сезонов или строго типизированной модели `season`/`episode`. [1: 26545, 26564–26640]

Next/Previous выбирает соседнюю группу с другим `pjs_parent`, затем пытается сохранить `title` предыдущего листа. Это совместимо с группировкой серий и озвучек, но не доказывает конкретный порядок вложенности. [1: 26733–26770]

Предполагаемая модель при соответствующих входных данных:

```text
Series → Season folder → Episode folder → выбранный leaf
       → leaf.data → playlist/load → response.file → HLS
```

Уровни Season/Episode здесь **LIKELY**, не реальные найденные названия папок. Код допускает другую вложенность. Каждый выбранный лист имеет своё поле `data` для запроса; уникальность дескрипторов между сериями не проверяется. Переключение вызывает `loadMedia`, а смена папки/Next сбрасывает позицию через `seek(0)` в соответствующих ветках.

Реальный сериал с полным embed/playlist не получен. Проверка нескольких серий и ответов API остаётся **UNKNOWN**. Синтетический вложенный playlist подтверждает работу обхода, но не каталог Cinemar.

## 17. Translations

UI показывает `title` у групп/листов; лист с `data` запускает playback. При переходе в соседнюю группу код предпочитает лист с тем же `title`. **LIKELY:** это сохраняет озвучку между сериями. Строгого поля `translation_id` и независимого API озвучек в wrapper не найдено. [1: 26602–26618, 26757–26765]

Если звук представлен audio renditions одного HLS, это другой механизм медиабиблиотеки; наличие такой поддержки в Hls.js не доказывает её использование данным каталогом.

Полного примера с несколькими переводами нет. Поэтому точная иерархия и работа озвучек сервиса остаются **UNKNOWN**, а не WORKING.

## 19. Stable vs temporary values

Наиболее устойчивый клиентский контракт в этой копии JS — дерево `folder`, выбор листа, opaque `data`, endpoint и объединение response. Это характеристика версии файла, не обещание совместимости сервиса.

Для будущей интеграции можно хранить логический content identifier и выбор серии/озвучки при подтверждённом соответствии каталогу. Нельзя объявлять постоянными embed suffix, `data`, `ssid`, `download` или HLS по одному сеансу. Нельзя вычислять `expiresAt` из внешнего вида timestamp без подтверждённой семантики.

`refresh` медиаисточника и обновление права/дескриптора — разные операции. Исследованный reload реализует только повторный запрос с имеющимся дескриптором. Если истёк сам дескриптор, потребуется разрешённый способ получить новую конфигурацию; такого отдельного механизма wrapper не показывает.

## 20. CinemapProvider architecture

Технически существующая архитектура J1ROX TV подходит для адаптера: `VideoProvider` отделён от `PlaybackSource`, а `CinemapProvider` сейчас явно возвращает unsupported. Поля URL, providerName, headers, expiresAt, quality и выбор контента уже представлены; `duration` и отдельный список subtitles в текущем `PlaybackSource` отсутствуют. Добавлять их имеет смысл после подтверждения интерфейса. [3]

Условная реализация после получения разрешённого контракта:

```text
MediaQuery(TMDB/title/year)
  → официальный mapping/search → Cinemar content ID
  → разрешённый embed/catalog interface → актуальный playlist
  → нормализация групп/серии/озвучки → логический PlaybackRequest
  → resolve: отправить выданный сервером descriptor в согласованный API
  → response.file + документированные metadata → PlaybackSource
  → проверка доступности/формата → AVPlayer
  → ошибка/истечение → refresh с актуальным descriptor
  → ограниченный retry либо ProviderResolver → другой провайдер
```

Из этой цепочки сейчас отсутствуют подтверждённые звенья:

1. `TMDB/title/year → Cinemar item`: найденный `/playlist/load` является resolver, не поиском каталога.
2. Стабильное получение полной актуальной конфигурации/дескриптора для стороннего клиента.
3. Подтверждённые правила lifetime/обновления дескриптора и доступа к HLS вне embed.
4. Проверенная модель сериалов/озвучек и совместимость реальных manifest/codecs с iOS.
5. Условия разрешённого использования интерфейса и рекламного механизма сторонним приложением.

В разрешённом adapter непрозрачный дескриптор следует воспринимать как выданное сервером значение и не генерировать самостоятельно. Повторные запросы должны быть ограничены; HTTP 4xx/5xx не считаются рабочим playback. При неизвестном сроке `expiresAt=nil`; устаревший URL не становится постоянным кешем. Headers добавляются только по подтверждённым требованиям интеграции, не для имитации чужого сайта.

Публично разрешённый embed потенциально можно показать в веб-контейнере при соответствующих условиях сервиса. Но embed не равнозначен API получения `PlaybackSource` для AVPlayer; подменять одно другим нельзя. API/UI/Atodo/Bundle ID в рамках этого отчёта не изменены.

## 22. Final conclusion

**Происхождение `currentItem.data` установлено на уровне доступного клиентского кода:** входной `options.file` → обратимое преобразование внешней строки → `JSON.parse` → исходное поле `data` листа → сохранённая ссылка в flatlist → выбранный `currentItem` → JSON serialization в POST. Значение уже доставлено входной конфигурацией; его исходная серверная генерация в клиенте отсутствует. Подпись или шифрование этого значения не доказаны.

**Полноценный CinemapProvider для AVPlayer пока не подтверждён и остаётся UNSUPPORTED.** Препятствие не в невозможности разобрать playlist: этот участок понятен. Недостаёт проверенного способа поиска и получения актуальной конфигурации/дескриптора, правил доступа/обновления и разрешения на использование потока вне штатного embed. Это вывод о текущих доказательствах, не утверждение, что оператор принципиально не может предоставить интеграцию.

Фильмы, сериалы и несколько озвучек не обозначаются WORKING без live-проверки. Источники приложения, workflow, signing и Bundle ID не изменены; новый IPA для документационного анализа не собирался.
